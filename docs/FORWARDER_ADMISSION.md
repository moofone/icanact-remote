# Forwarding admission and reclamation

Affected invariants: REMOTE-1 (connection-owned endpoints), REMOTE-2 (owner-preserving bounded admission), REMOTE-3 and REMOTE-4 (exact-session receipts and stale-token rejection), and REMOTE-5 (count, retained bytes, lifetime, shutdown).

## Endpoint migration

Each `AskForwarder` now serves exactly one destination physical session and one return physical session. During connection setup, call `forwarder.bind_destination(connection)` once and retain the returned opaque, `Copy` `ForwardDestination`. Pass that receipt, rather than cloning a `RemoteConnection`, to every `try_forward_actor_ask_*` call. The first scoped responder cold-binds the return endpoint; subsequent responders must belong to that same physical return stream. A service forwarding from several source connections keeps one forwarder per source/destination session pair. On either connection's replacement, construct a new forwarder and bind its new destination receipt; drain or shut down the old forwarder separately. A receipt does not discover, reconnect, or retarget a connection.

Destination registration has exactly one slot. A second binding or exhausted non-reissued endpoint identity returns `GossipError::WriteQueueFull`. A closed forwarder, an unbound receipt, or another forwarder's receipt returns `GossipError::Shutdown` before claiming the reply. A responder from another physical return stream returns `GossipError::InvalidConfig`; equal addresses do not establish stream identity. During first return-endpoint initialization, one publisher owns construction and racing publishers receive `WriteQueueFull`, rather than allocating duplicate tables, waiting on a lock, or building a hidden backlog. Once initialized, endpoint access is direct, without a registry/address lookup or per-job reference-count change.

The forwarder and each worker retain their endpoint owner only during cold setup. Queued jobs contain payload owners, actor metadata, deadlines, numeric charges, and an opaque numeric reply token. They contain no `RemoteConnection` or owned `AskResponder`. Workers borrow the immutable destination connection. Reply tokens carry a non-reissued endpoint identity, slot index, and full generation; they never contain a dereferenceable pointer. Their owning `ReplySession` keeps the exact return stream and fixed token storage alive until the queue and workers are reclaimed. No stale token can operate on another endpoint or release a reused slot.

`AskContext::responder()` is scoped to its context. Forwarding synchronously transfers that borrowed claim to connection-owned token storage. The transfer remains provisional until the ingress ring has accepted the job: queue rejection cancels only that unpublished token and restores the original claim for a retained sibling. Successful publication commits before any waker, drain, or potentially unwinding callback. A responder already claimed by a sibling still produces an admitted forward with a terminal undeliverable/error observation, preserving duplicate-claim accounting without retrying or sending a second reply.

## Native payload ownership

`ForwardPayload` and `ReplyPayload` are unique owner envelopes. Moving a spare-capacity `Vec`, boxed slice, static slice, native aligned allocation, aligned receive-pool checkout, or typed pooled owner into them preserves the original allocation and its complete retained-capacity charge. Native pooled storage is a concrete nonrecursive enum; moving a payload through `PooledPayload::from_owned` and back flattens the envelope instead of allocating another wrapper. Serializer owners continue to charge their archive, scratch and fixed sharing-table capacities. The route writer keeps these owners in `HeaderInlinePooled`, including the 32-byte uncompact/request-id framing path. Leased response streaming likewise retains the native owner.

These envelopes deliberately have no implicit `Clone`. For genuine fanout, use `into_shared()` once during explicit sharing setup and `shared_clone()` for subsequent aliases. Every alias retains and charges the complete owner's capacity. `shared_clone()` rejects a unique owner; it never silently copies or allocates a promotion. `AlignedBytes::into_range` consumes a unique owner to make a subview while preserving that capacity. Its borrowed `slice` API requires explicit `into_shared()` for native aligned owners. `ReplyPayload::as_bytes` now returns a borrowed byte slice. `ForwardPayload::into_bytes`, `AlignedBytes::into_bytes`, and copying compatibility APIs remain explicit boundaries that may allocate shared metadata or copy bytes; native forwarding and reply writer paths do not invoke these promotions.

The public `RemoteConnection::ask_actor_frame_owned`, `ask_actor_frame_no_timeout_owned`, and `ask_actor_frame_deferred_owned` paths retain native request ownership through routed admission. The scoped `PendingAsk`/`DeferredAsk<'session>` result borrows the exact submitting connection tracker without a per-request `Arc`. Keep the session in scope while its handles run; move the session into a spawned task before submitting, rather than exporting a handle. Absolute submission deadlines, cancellation, non-reissued IDs and native request/reply ownership remain unchanged. The public generic `write_pooled_control`/`write_pooled_ask` methods still use `HeaderPooled`, whose writer conversion calls `into_remaining_bytes`; this compatibility branch can allocate owner metadata and is distinct from native forwarding's `HeaderInlinePooled` branch. Broader raw/direct/deferred compatibility APIs are not covered by a blanket zero-incidental-cost claim.

## Explicit budgets and overload

`AskForwarder::new_with_limits` clamps worker count to 1–64, queue capacity to 128–65536, and the retained-owner byte budget to 1–u32::MAX. Across the entire forwarder, at most `capacity + 16` jobs own count admission. Each worker has a fixed `capacity`-entry ingress ring, a preallocated `capacity + 16`-entry deadline index, and 16 pinned future slots. The return endpoint has exactly `capacity + 16` claim slots, at most 65552, shared across workers. Destination and return registrations each retain at most one transport session. These startup metadata allocations are bounded by the configured worker count and capacity; increasing either increases that declared metadata footprint. They are distinct from the aggregate request/fallback payload budget (64 MiB by default). Each request and both terminal fallback owners are charged by full retained capacity, including unused Vec capacity. Receive replies retain their independently bounded transport owners.

Admission uses preallocated rings, numeric count/byte counters, and fixed reply-token slots. A failed compare-exchange, insufficient count/bytes/token slots, or a full selected worker ring returns `GossipError::WriteQueueFull`; closure returns `GossipError::Shutdown`. Admission does not wait, spin, allocate another job node, or scan other workers for capacity. Round-robin selection therefore permits local rejection while another worker has space. Accepted jobs are never silently dropped: normal expiry/completion or forced shutdown supplies terminal accounting. The configured operational lease is five minutes by default, including queue wait, destination response and reply handoff; no-application-timeout calls remain subject to it. Expiry cancels only the ask and never diagnoses or evicts a healthy transport.

Count/byte charges and reply tokens are numeric while queued and become borrowed RAII guards while waiting or in flight. Receivers reconstruct guards without reacquiring admission. Cancellation, payload panic and worker shutdown cancel only the exact reply token and return all charges. Receiver cancellation drains the ingress ring; a producer crossing cancellation completes any final drain. Drain isolates a hostile payload destructor so later accepted entries are still reclaimed. Final shutdown waits for worker exit and all already-admitted publishers before reconciling outcomes. Existing deadline and pinned-future scheduling remain: futures stay in preallocated pinned slots and are dropped in place, and stale slot wakes can cause only a harmless current-slot poll.

Ordinary successful results await bounded return-writer admission within the remaining deadline. An expired job makes exactly one nonblocking terminal attempt on the reserved immediate lane; ordinary-lane saturation therefore does not itself deny terminal control progress. Immediate-lane rejection is observed as `ReplyUndeliverable`, never as success, and does not release exclusivity for a duplicate response. The writer's separate count/byte admission and operational controls still apply.

## Evidence and limits

The existing 128-admitted-plus-overflow regression now includes `AskContext` construction, scoped responder construction, complete public forwarding admission, destination validation, numeric reply transfer, queue publication, overflow and original-claim rollback in its measured scope. It asserts zero calling-thread allocations/reallocations and constant return-stream, endpoint, budget and queue owner counts while all 128 jobs remain queued. It then checks expiry reclamation and subsequent admission. Cold connection/endpoint creation and executor work are outside that counter. The independent positive allocation control remains mandatory.

Additional deterministic controls exercise:

- Real TLS destination ask and exact returned wire response; foreign-forwarder receipt rejection; same-address foreign return-stream rejection; physical successor and address-alias rejection followed by successor success
- An acknowledged pre-enqueue publication pause, forced receiver closure, shutdown waiting for the publisher, restored rejected claim, and exact zero admitted/completed outcome accounting
- Nonvacuous ordinary-lane saturation followed by reserved terminal response on the wire and duplicate suppression
- Payload-destructor panic while draining real reply tokens, subsequent slot reuse, stale-token cancellation rejection, and a successor response on the wire
- Zero measured owner-wrapper allocations for spare-capacity Vec through both forwarding/reply envelopes, native aligned views, advanced byte-pool owners through 128 forwarding/reply/pooled roundtrips, serializer owners, and aligned receive-pool owners; original pointers, full capacities, final pool return, and explicit sharing/Bytes allocation positive controls
- Real route-bind warmup followed by `RemoteConnection` timed and no-timeout native asks: original pointer/capacity while the actual writer command is queued, unchanged stream owner count, calling-thread allocation counter, cancellation, complete physical frame output and continued transport health

Existing full forwarding success/timeout/after-timeout integration, normal-queue retry, sibling-claim exclusion, pointer provenance, partial-owner rejection, pinned `!Unpin` address/panic/reuse, and queued/waiting/in-flight cancellation controls remain mandatory. Request counts, deadlines, assertions and feature gates are preserved.

The test-only allocation helper measures allocations, reallocations and requested bytes only on the calling thread. It cannot establish cross-thread or complete end-to-end allocation/copy performance. Transport correlation/write work, timer/waker internals, whole-process overload plateau, and repeated same-host release comparisons require the unchanged host validation and appropriate benchmarks. All tests and measurements described here are authored controls, not remotely executed passes. Whole-tree architecture status remains UNPROVED.
